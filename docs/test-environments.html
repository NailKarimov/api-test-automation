Shared sandbox or private copy: where to test the code

С 18.10.2026 тесты Petstore гоняются против своей Docker-копии, которая в каждом прогоне стартует с чистыми данными. Причина — за неделю публичная песочница трижды сделала сборку красной без единого изменения в нашем коде. После переезда три «дефекта» оказались проблемами окружения.

Since 18.10.2026 the Petstore tests run against our own Docker copy that starts with clean data in every run. The reason: in one week the public sandbox turned the build red three times without a single change in our code. After the move, three "defects" turned out to be environment problems.

      Тестируем версию из образа, а не живую — разрыв виден благодаря oasdiff. Плюс один контейнер в CI, около 10 секунд на старт.

      We test the image's version, not the live one; oasdiff keeps the gap visible. Plus one container in CI, about 10 seconds to start.

      Код тестируй в окружении, которое контролируешь и сбрасываешь. Развёртывание — заголовки, TLS, лимиты, доступность — проверяй на самом развёртывании. И держи эти проверки отдельно, чтобы одни не прятали другие.
      Test the code on an environment you control and reset. Test the deployment (headers, TLS, rate limits, availability) on the deployment itself, and keep the two apart so one cannot hide the other.
